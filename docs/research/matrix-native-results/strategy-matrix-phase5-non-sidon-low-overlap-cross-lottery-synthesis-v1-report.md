## 3. DELTA_SIDON shape by k — growing / peaking / declining / lottery-specific

`DELTA_SIDON(k)` (the **absolute** arm-B-minus-Sidon gap) is **not**
monotonic in any of the three lotteries — each rises from `k=3`, reaches an
interior maximum, then declines toward `k=20`, while staying strictly
positive throughout (so Q2 holds despite the non-monotonicity):

```text
BIG_LOTTO:           PEAKING_AT_K15  (+0.00079 -> +0.00887 @k=15 -> +0.00849 @k=20)
DAILY_539:           PEAKING_AT_K15  (+0.00019 -> +0.00181 @k=15 -> +0.00144 @k=20)
POWER_LOTTO_zone1:    PEAKING_AT_K5   (+0.00280 -> +0.00923 @k=5  -> +0.00526 @k=20)
```

**Common**: peaking, not monotonic growth or monotonic decline, in all
three. **Lottery-specific**: the peak location itself splits 2-1 — BIG_LOTTO
and DAILY_539 both peak at `k=15`; POWER_LOTTO Zone-1 peaks much earlier, at
`k=5`, and has already been declining for three ladder rungs by the time the
other two lotteries reach their peak.

**A separate, previously-unstated finding this synthesis surfaces**: the
**relative** `REL_GAIN_OVER_SIDON(k)` ratio does *not* share
`DELTA_SIDON`'s peak location. It peaks at **`k=5` in all three lotteries**
and then declines monotonically through `k=20` in all three — a materially
cleaner cross-lottery invariant than the absolute delta's shape:

```text
BIG_LOTTO:           5.91x (k=3) -> 6.08x (k=5, peak) -> 4.74x -> 2.50x -> 1.64x (k=20)
DAILY_539:           2.65x (k=3) -> 2.68x (k=5, peak) -> 1.90x -> 1.40x -> 1.15x (k=20)
POWER_LOTTO_zone1:    3.34x (k=3) -> 3.48x (k=5, peak) -> 1.48x -> 1.14x -> 1.09x (k=20)
```

Neither per-lottery sealed report states this shared `k=5` ratio-peak
explicitly: B649's own report describes its ratio only as "shrinking toward,
but never below, 1x" starting from `k=3` (true, but it omits the small `k=3
-> k=5` rise that precedes the shrink); T539's and P638 Zone-1's reports
discuss `DELTA_SIDON`'s own shape but not the ratio's shape at all. This is
this synthesis's own analysis, not a restatement of a previously-published
number.

## 4. Common geometry properties

All independently confirmed across all three lotteries directly from each
cell's own sealed per-`k` geometry (`common_geometry_invariants` in the
result artifact):

- **`max_pairwise_overlap` never exceeds `1`**, at any tested `k`, in any of
  the three lotteries (`0` at `k<=5`, `1` at `k in {10,15,20}` — the
  disjoint-block region shrinks with pool size: BIG_LOTTO `49//6=8`,
  DAILY_539 `39//5=7`, POWER_LOTTO Zone-1 `38//6=6` full disjoint blocks
  available, all `>=5` so `k<=5` stays fully disjoint in every lottery).
- **Zero duplicate tickets**, at every tested `k`, in all three (frozen
  invariant, asserted at runtime by each source, re-confirmed here).
- **`overlap_profile` keys are a subset of `{0, 1}`** in all three — the
  full pairwise-overlap distribution, not just its max, stays within
  `{0, 1}` everywhere tested.
- **`REL_LIFT_RANDOM(k)` is monotonic non-decreasing** in `k`, in all three
  lotteries (unlike either Sidon-relative measure in §3, the vs-random
  relative lift simply keeps growing with more tickets, uniformly).
- **Mean pairwise overlap and reuse dispersion both increase with `k`** in
  all three (more tickets forces more number reuse in every lottery) —
  shared qualitative trend; magnitudes differ (see §5).

## 5. Lottery-specific geometry differences

- **Full pool coverage**: DAILY_539 and POWER_LOTTO Zone-1 both reach full
  unique-number coverage within the tested ladder (`39/39` by `k=15`,
  `38/38` by `k=20`); BIG_LOTTO does **not** — it caps at `48/49` from
  `k=10` onward and never uses its pool's highest number (`49`) at any
  tested `k`, a structural consequence of the shared constructor's
  lexicographic tie-break rule, not a BIG_LOTTO-specific code path.
  Observed within the tested `k<=20` ladder only — not a proven asymptotic
  property, and not tested past `k=20` here.
- **Relative-lift magnitude at `k=20`**: POWER_LOTTO Zone-1 is the clear
  outlier at `+11.89%`, versus BIG_LOTTO `+6.95%` and DAILY_539 `+5.87%` —
  roughly double the other two, consistent with (not proof of) its smaller
  pool forcing overlap, and hence separation from random, earlier and more
  strongly.
- **Mean pairwise overlap at `k=20`**: POWER_LOTTO Zone-1 `0.826` >
  BIG_LOTTO `0.663` > DAILY_539 `0.616` — ranks oppositely to pool size
  (`38 < 39 < 49`), consistent with a smaller pool forcing more reuse at the
  same `k`.
- **`DELTA_SIDON` peak location** (§3): 2-of-3 lotteries share `k=15`; the
  third (POWER_LOTTO Zone-1) does not. This is the one place where "2 of 3
  agree" is the most that can honestly be said — not "common to all three."

## 6. A naming indirection, not a data gap

The Owner packet named the required B649 input
`GREEDY_MIN_OVERLAP_CONSTRUCTOR_B649_V1` as if it were a standalone sealed
file, matching T539's and P638 Zone-1's own file-per-cell convention. On the
live repository, no such standalone file exists: B649's arm B is embedded
(arm letter `b`) inside the earlier, differently-named 4-arm
`DIVERSIFICATION_CONSTRUCTOR_FRONTIER_B649_V1` cell (arms A=Sidon, B=greedy,
C=bounded optimizer, D=random-expected), because that cell predates the
per-lottery `GREEDY_MIN_OVERLAP_CONSTRUCTOR_{LOTTERY}_V1` naming convention
T539 and P638 Zone-1 established afterward. The substance is not ambiguous:
the frontier cell's own Method section names arm B explicitly as
`GREEDY_MIN_OVERLAP_CONSTRUCTOR_B649_V1`, and both T539's and P638 Zone-1's
own `REPLICATES:` identity blocks cite it as their origin. This synthesis
reads B649's arm B from that embedded location
(`diversification-constructor-frontier-b649-v1-result.json` → `q.b`,
`delta_random.b`, `delta_sidon.b`, `geometry.b`) and records both the
file-level `source_matrix_variant_id` and the `arm_b_constructor_id` cited
from the report's Method section, so the indirection is traceable rather
than silently resolved. Arm C (bounded optimizer) and arm D live in the same
file and are not read by this synthesis beyond what `load_source`'s identity
check touches.
